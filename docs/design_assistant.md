# 设计助手 SOP —— 粗需求 → 可评审设计稿

> **解决什么:** 需求清单只写了大概业务逻辑时,AI 不再"拍脑袋产 20 张表"或"卡壳产不出"。
> 动作顺序固定为:**先查旧账(设计知识库) → 匹配同类系统 → 出草案 → 主动补客户没想到的 → 覆盖自检 → 人工过目 → 才落定义**。
>
> 本 SOP 已内嵌进 Web 平台出方案/流程图/ER 的提示词
> (`backend/app/services/plan.py`、`flowchart.py`、`design.py`)。
> **依赖是单向的**:方案=唯一源头(写全字段/规则/关系)→ **流程图只依方案** → **ER 依「方案 + 业务流程图」**。
> 参考资料(用户上传的文档 + 本部署已建项目语料,不含内置样本)**只在出方案时使用**。
> 定义格式见 `docs/schema_doc.md`。

---

## 0. 三条铁律

1. **先看资料后设计**:先通读用户上传的文档(已有系统/需求/会议),再看 `data/knowledge/corpus.md`、`patterns.md`(本部署已建项目语料)。**不许跳过资料从零想。**
2. **三档置信度标注**,每个未定项必须标:
   - ●(确定)—— 需求原文/常识明确,直接采用;
   - ▲(推断)—— 同类系统惯例,给出默认值,请人确认;
   - ?(存疑)—— 没有依据且影响大,必须人答。
3. **草案先行,定义后置**:先产出**设计稿(DESIGN.md 形态,带 ▲)**交人工过目;确认后才写 `sheets/*.json`。**绝不在未过目时 build。**

---

## 1. 读知识库(1 分钟)

知识库在 Web 端**自动维护**(建/改项目或夜间批处理时重建;也可 `POST /api/knowledge/refresh`)。**无需手工命令。**

- `data/knowledge/corpus.md` —— 每张表的字段、类型、子表、关联、`uiNote`(界面手工意图)。**"过去怎么建的"看这里。**
- `data/knowledge/patterns.md` —— 跨项目共识:枚举字典、常见字段语义码、表关系图、自动化样例、领域设计文档索引。
- `data/knowledge/corpus.json` —— 机器可读全量(需精确检索/统计时用)。
- 历史项目的 `DESIGN.md` / `UI_manual_config.md` —— 领域决策与口径的完整上下文,匹配到同类项目时**必读**。

---

## 2. 需求分类与历史匹配

1. 从需求里抽**实体名词**(客户/合同/项目/门店/人员/设备…)和**动作**(申请/审批/回写/统计)。
2. 在 `corpus.md` 的项目标题、表名、字段 label、`patterns.md` 的枚举与关系图里找交集 → 得出**候选参考项目**。
   > 语料**全部来自用户自己上传/建立的资料**(`data/projects/` 下已建项目 + 本项目上传文档),
   > 无任何内置样本;命中"同类"即复用其表/字段/关系。
3. 判定相似度并说明:
   - **同类**(如又是"XX 管理 + 合同 + 人员成本")→ 直接以命中的样本为骨架裁剪;
   - **部分相似**(只借某模块)→ 借该模块的表/字段,其余新设计;
   - **全新领域**→ 按第 3 步"标准表型"从通用模式搭,并在草案里显式声明"无历史参考,风险高"。

> 示例:新需求"健身房连锁门店管理" → 命中门店加盟样本(门店/加盟/区域/合同/申请单),
> 直接复用其 `store/region/storecontract/relocate/closure` 结构与"申请单审批后回写主表"的范式。

---

## 3. 模块与表单草案(含"为什么有这张表单")

**模块**取自需求清单的「功能模块」(顺序一致);每个模块下逐张列出**表单**并注明角色与依据
(此阶段用**中文业务名**,不写字段 key —— 那是 ER 阶段的产物,方案里不出现):

| 模块 | 表单名 | 角色 | 依据 | 置信 |
|---|---|---|---|---|
| 客户管理 | 客户 | 主数据 | 需求§2 明确 | ● |
| 合同管理 | 合同 | 单据 | 用户资料/同类项目惯例 | ▲ |

**标准表型(客户没想到时主动补,按需裁剪):**

- **主数据/档案**:每条一个"编码+名称+状态(启用/停用)+备注+附件";常配"列表按 XX 筛选"。
- **字典/配置表**:当"存名称还是代码"有歧义、或代码要参与编号拼接时,单独建字典表。
- **单据/申请单**:单号(流水号或年月)+ 申请人/部门(系统字段)+ 日期 + 关联主数据 + 明细子表 + 状态 + 备注。
- **关联/流水记录**:操作留痕、跟进记录、日志类(通常 useOwner=true)。
- **统计口径**:能由字段汇总的不建表(用列表视图/SQL);需要落库的汇总字段标"代码回写 RO"。

---

## 4. 字段 / 关系 / 枚举草案

- **字段**:优先复用 `patterns.md` 的**常见语义码**(如 `remark`/`pname`/`pcode`/`customer`/`prj`/`docno`/`items`/`total`/`is_paid`),保持跨项目一致;类型映射见 `schema_doc.md` 控件表。
- **关系**:参考 `patterns.md` 的关系图,`query` 控件 + 先建被引用表;一对多明细用**子表**(注意子表列类型受限)。
- **枚举**:优先命中 `patterns.md` 已有枚举(如"人员状态/合同类型/评价等级/是/否"),没有再新建 `dicts.json`;一次性枚举可直接写 `options`。
- **命名**:字段 key 必须字母开头、纯字母数字、无下划线,且避开平台自带名(`Name/SeqNo/Status/…`)——见 `schema_doc.md「key 命名规则」`,`check` 会拦。

---

## 5. 主动补全(核心:把客户漏掉的补进去)

对每张表套用下面的**漏项自检表**,凡需求没提、但同类系统通常都有的,**补进草案并标 ▲**(给默认值,请客户确认是否要):

- [ ] **唯一/编码**:有没有业务含义的编码字段?要不要唯一?
- [ ] **状态/启停**:有没有生命周期状态?用下拉还是开关?默认值?
- [ ] **日期**:创建日期以外,业务上要哪些日期(生效/到期/预计/实际)?默认今天?
- [ ] **人员/部门**:除了创建人,还要"负责人/经办人/参与人/所属部门"吗?单选还是多选?
- [ ] **明细子表**:单据是不是要"一行多条目"(合同明细、报销明细、任务明细)?
- [ ] **金额/小计**:主表金额=明细合计?要不要已收/未收、已开票/未开票?
- [ ] **附件/图片**:合同扫描件、发票、现场照片、资质证明?
- [ ] **备注**:几乎每张表都需要 `remark`。
- [ ] **关联**:这张表挂在谁下面?要被谁引用?
- [ ] **回写/自动化**:提交后要不要改别的表/生成记录/发通知?(见 `schema_doc.md` 自动化)
- [ ] **审批**:要不要审批流、驳回?(工厂 API 配不了,列入界面配置清单)
- [ ] **报表/分析**:客户要看的统计,能用字段汇总还是要 SQL 视图?(**看板/报表不建表**:不进流程图与 ER、不生成应用,由氚云端 SQL 报表另配)
- [ ] **历史/归档**:人员离场、项目结项、门店闭店,要不要归档历史?

> 输出形态举例如下,让人一眼能审:
>
> **▲ 补:合同表建议加「合同到期日期」** —— 同类 `storecontract` 都有,用于到期提醒;默认加,
> 如不需要请划掉。**▲ 补:申请单建议加「审批状态」** —— 需求未提审批,先按"无审批、提交即生效"
> 实现,审批留二期;若本期要审批请说明。

## 6. 覆盖自检(防漏,交付前跑一遍)

画一张**需求条目 → 设计落点**对照表,逐条销账,孤儿与未被覆盖的都要显式列出:

| 需求条目(原文序号/要点) | 落点 | 状态 |
|---|---|---|
| §1 客户信息管理 | customer 表 + customer 菜单视图 | ● 覆盖 |
| §3 自动算毛利 | project.profit 公式/回写 | ▲ 待定口径 |
| §5 提醒到期 | 定时任务 + 通知 | ▲ 本期是否做 |
| (无来源) | project.ptag 项目标签 | ? 需求未提,补的 |

- **未被覆盖的需求条目** → 补设计或明确"不做及原因"。
- **无需求来源的设计项** → 要么是漏项补全(正常,标 ▲),要么是过度设计(**删**)。

---

## 7. 输出与过目

1. 在 Web 工作台产出**系统设计方案(plan.md)**,格式为**客户可交付版**:
   **标题1=模块、标题2=表单**,每个表单下用**阿拉伯数字**逐项列出「业务内容」
   (字段**中文名** / 子表明细 / 业务规则 / 金额与数量口径 / 流程触发);
   末尾附「模块与表关系」「关键口径」「待确认」。
   **不写字段 key、不写界面配置** —— 那是后续 ER 阶段(见 §8.12)的事,不进客户方案。
2. **人工过目**(唯一不可省):重点审 **▲/? 项、表单数量、模块与表关系、口径、漏项补全是否合理**;
   可在方案编辑页直接改 Markdown。
3. 确认后生成**表单结构(sheets+automations)**:ER 阶段**依据「方案 + 业务流程图」**
   (流程图用于判断自动化)把方案里的「表单 / 字段(中文名)」落实为字段 key / 控件 / 子表 / 自动化;
   **看板/报表不建表**;经引擎离线校验 → 再点「生成氚云应用」部署。

## 8. 设计自检 12 问(起草后逐条自答)

1. 同类历史系统里,这个模块**通常还有哪张表**我没建?
2. 每张表的"名称/编码/状态/日期/负责人/备注"六件套齐了吗?
3. 明细子表的小计与主表金额对得上吗?谁算?
4. 关联方向对不对?被引用的表先建了吗?
5. 枚举是复用现有还是新造?存名称还是代码?(见 `schema_doc.md`)
6. 哪些是**代码回写的只读字段**?口径写清了吗?
7. 有没有"提交后要连带改别的表"的动作?→ 该上自动化还是 .cs?
8. 审批要不要?本期还是二期?
9. 客户漏提但业务上**必然需要**的字段,我补了几条?都标 ▲ 了吗?
10. 需求每条都有落点吗?有没有孤儿设计?
11. 有没有触到平台**未实证**的能力(子表内关联列、定时触发…)需要先验证?
12. 这次交付要附哪些**界面手工配置清单**项?(必填/只读/审批/联动/视图)
